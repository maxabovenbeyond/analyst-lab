# Проектирование API сервиса доставки v1

Базовый URL: `/v1`. Формат: JSON. Ошибки: RFC 9457 (application/problem+json).
Аутентификация: Bearer-токен; роль (CUSTOMER / SHOP / SUPPORT) определяется по токену.

## Эндпоинты

> Общее правило: все эндпоинты, кроме /auth/* и /webhooks/*, требуют токен → 401 без токена.
> Для эндпоинтов с {id}: 404 — объект не найден, 403 — объект чужой или роль не подходит.
> В колонке «Ошибки» ниже указаны только специфичные для эндпоинта.

## Решения

1. **Повтор вебхука → 200, а не 409.** Провайдеры доставляют вебхуки по принципу at-least-once:
   повторяют, пока не получат 2xx. Ответ 409 провайдер воспримет как сбой доставки и продолжит
   повторы. Факт оплаты уже учтён — повтор распознаём по `provider_payment_id`, ничего не меняем,
   отвечаем 200.

2. **Фильтры API и индексы.** На индексы опирается №6 `GET /shops/{shopId}/orders?status=PAID&created_from`:
   ~50 магазинов × опрос раз в 15 с ≈ 200 запросов/мин. Каждый фильтр API — это SQL-запрос, поэтому
   API разрешает фильтры и сортировки только по индексированным полям, иначе каждый вызов — Seq Scan.
   Находка: запрос фильтрует по shop_id + status + created_at, а индексы есть только
   (shop_id, created_at) и (status, created_at). Добавлен индекс `orders (shop_id, status, created_at)`.

3. **Защита №12 от двойного одобрения.** Проверка и смена статуса — одна атомарная операция:
   `UPDATE claim SET status = 'APPROVED' ... WHERE id = :id AND status = 'OPEN' RETURNING id`.
   Второй оператор получает 0 строк → 409 «Претензия уже обработана». Наивный вариант
   «прочитать → проверить → обновить» не защищает: оба оператора успевают прочитать OPEN
   (проверено экспериментом в модуле 2). Страховка на уровне БД — UNIQUE на ключе возврата `CLM-<id>`.

4. **Кто может отменять заказ.**
   | Кто | Из каких статусов | Как | Причина |
   |---|---|---|---|
   | Клиент | AWAITING_PAYMENT, PAID | `POST /orders/{id}/cancel` | Клиент отменил |
   | Поддержка | всё до IN_DELIVERY | `POST /orders/{id}/cancel` | указывает оператор (US-09) |
   | Магазин | PAID | `POST /orders/{id}/decline` | Магазин не может принять |
   | Система | AWAITING_PAYMENT | таймер, без API | Не оплачен |
   | Система | PAID | таймер, без API | Магазин не подтвердил |
   | Система | AWAITING_COURIER | событие от службы доставки | Курьер не найден |

   После начала доставки (IN_DELIVERY) отмена невозможна — только претензия после получения.
   Права клиента на отмену — допущение: истории нет, нужно подтвердить у продукта (добавить US).

5. **Привязка карты (US-12).** Данные карты не проходят через наш сервер (иначе требуется
   сертификация PCI DSS). Карта вводится на форме платёжного провайдера, нам приходит только
   токен. Храним: токен, последние 4 цифры, платёжную систему, срок действия.
   Эндпоинты:
   - `POST /me/cards` → 201 + `confirmation_url` (ссылка на форму провайдера)
   - `POST /webhooks/payments` (событие «карта привязана») → сохраняем токен
   - `GET /me/cards` → список карт в маскированном виде
   - `DELETE /me/cards/{cardId}` → 204, токен удаляется и у провайдера
   Альтернатива: галочка «Сохранить карту» при первой оплате (US-15).

6. **Время в API.** Все даты передаются в формате ISO 8601 в UTC
   (например, `2026-09-30T16:20:18Z`). Перевод в местное время — на стороне клиента.
   Входные параметры (created_from) принимаются с любым смещением.

   Шпаргалка: как выбрать код
Запрос технически сломан (JSON, типы)?          → 400
Нет токена / неверная подпись?                  → 401
Нет прав на действие или объект?                → 403 (или 404, чтобы скрыть)
Объекта нет?                                    → 404
Данные понятны, но нарушают правила?            → 422
Объект в неподходящем состоянии?                → 409
Слишком часто?                                  → 429
Упало у нас?                                    → 500 / 503
Всё хорошо:
   создали новый объект?                        → 201 + Location
   приняли, но сделаем позже?                   → 202
   нечего возвращать?                           → 204
   иначе                                        → 200

Порядок проверок важен: сначала 401 (кто ты), потом 403 и 404 (можно ли и есть ли), потом 400 и 422 (данные), потом 409 (состояние). Именно так сервер и обрабатывает запрос.


Чтобы получить заказы магазина, отправьте `GET` на `/v1/shops/{shopId}/orders`
с Bearer-токеном в заголовке `Authorization`. `shopId` передаётся в пути:
обязательное целое (int64), например 12.

Необязательные параметры в query:
- `status` — один из статусов заказа (например, PAID);
- `created_from` — дата-время ISO 8601, заказы начиная с этого момента;
- `limit` — размер страницы, 1–100, по умолчанию 50;
- `cursor` — закладка из `next_cursor` предыдущего ответа.
Фильтры соответствуют индексу orders (shop_id, status, created_at).

При успехе — `200` и страница заказов (`OrderList`): массив `items` с заказами
и `next_cursor` — закладка для следующей страницы; `null` — страниц больше нет.
У каждого заказа всегда есть id, shop_id, status, items_amount, delivery_fee,
created_at; могут прийти items и cancel_reason.

`400` — неверные параметры (limit вне 1–100, неизвестный статус).
`401` — нет токена или он недействителен.
`403` — магазин чужой. Отвечаем 403, а не 404: существование магазина не секрет.


Чтобы получить карточку заказа, отправьте GET на /v1/orders/{orderId} с Bearer-токеном в заголовке Authorization. orderId передаётся в пути: обязательное целое число (int64), например 8001. Тела у запроса нет.

При успехе вернётся 200 и объект заказа. Всегда приходят id, shop_id, status, items_amount, delivery_fee, created_at. Дополнительно могут прийти items (позиции заказа) и cancel_reason (только для отменённых).
401 — нет токена или он недействителен: нужно войти заново.
404 — заказа не существует или он чужой (факт существования чужого заказа скрываем).
