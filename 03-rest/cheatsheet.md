# Шпаргалка: REST API и интеграции

## 1. Контракт
- Контракт (OpenAPI) — меню ресторана: что можно заказать, в каком виде, что принесут и что скажут при отказе.
- Contract-first: сначала контракт → согласование → код. Плюс: параллельная работа бэкенда, фронта и тестов.
- Code-first: контракт генерируется из кода. Риск — дрейф: документация расходится с поведением.

## 2. Метод = намерение
| Метод | Смысл | Безопасный | Идемпотентный |
|---|---|---|---|
| GET | прочитать | да | да |
| POST | создать / выполнить команду | нет | нет (нужен Idempotency-Key) |
| PATCH | поправить поля | нет | обычно нет |
| PUT | заменить целиком | нет | да |
| DELETE | удалить | нет | да |

**Команда vs PATCH.** Смена статуса — бизнес-операция: кто может, из каких статусов, какие данные нужны,
какие последствия. → `POST /orders/{id}/cancel`. Сервер владеет автоматом состояний.
PATCH — для полей без правил (цена, наличие, имя).
Правило: есть название в языке бизнеса, правила или последствия → команда.

## 3. Коды ответов
Порядок проверок: 401 → 403/404 → 400/422 → 409 → успех.

| Код | Смысл | Пример |
|---|---|---|
| 200 | сделано | прочитали, отменили |
| 201 | создан объект (+ Location) | создали заказ |
| 202 | принято, сделаем позже | SMS, импорт Excel |
| 204 | сделано, тела нет | удалили карту |
| 400 | запрос сломан технически | битый JSON, limit=abc |
| 401 | не знаю, кто ты | нет токена, неверная подпись |
| 403 | знаю, но нельзя | магазин отменяет заказ |
| 404 | нет такого (или скрываем чужое) | чужой заказ |
| 409 | мешает состояние объекта | отмена доставленного |
| 422 | данные нарушают правила | нет причины отмены |
| 429 | слишком часто (+ Retry-After) | SMS-коды |
| 5xx | сломался сервер, можно повторить | |

- **409 или 422?** Поможет ли исправить запрос? Да → 422. Нет, мешает состояние → 409.
- **403 или 404?** Секретен ли сам факт существования? Заказ — да (404). Магазин — нет (403).
- **Пустой список → 200**, не 404: список существует, просто пуст.
- Антипаттерн: `200 {"success": false}` — мониторинг и провайдеры считают это успехом.

## 4. Идемпотентность ⭐
**Повтор той же операции даёт тот же результат, что и один вызов.** Данные меняются, но один раз.
Аналогия: кнопка лифта — нажали 5 раз, лифт приехал один.
Не путать с «безопасным» запросом (GET): он вообще ничего не меняет.

Зачем: в интеграциях запросы повторяются (сеть оборвалась → не знаем, дошло ли → шлём снова).

Как обеспечить:
| Способ | Пример у нас |
|---|---|
| Ключ идемпотентности от клиента | `Idempotency-Key` в POST /orders |
| Журнал обработанных событий | `webhook_event` по `event_id` → 200 DUPLICATE |
| UNIQUE в базе | `provider_payment_id` у платежа |
| Целевое состояние уже достигнуто | повторная отмена → 200 без изменений |
| Ключ в запросе к внешней системе | `CLM-<id>`, `REFUND-<payment_id>` при возврате |

## 5. Вебхук
HTTP-запрос, который внешняя система отправляет НАМ, когда у неё что-то произошло.
Аналогия: дверной звонок вместо того, чтобы выглядывать в окно (опрос).

| Проблема | Защита |
|---|---|
| Кто звонит? (подделка) | Подпись HMAC на общем секрете → 401 |
| Звонок повторился (at-least-once) | Журнал по event_id + UNIQUE → 200 DUPLICATE |
| Звонок «невовремя» (оплата после отмены, не по порядку) | Проверка текущего состояния перед действием |

Порядок обработки — КПП: подпись → формат → журнал → заказ → сумма → запись.
Первая неудачная проверка останавливает обработку и сразу отвечает.
Шаги с БД — одна транзакция: при ошибке откатывается всё, включая журнал.
Обработчик отвечает быстро (< 1 с). Долгое (SMS, чек, возврат) — в фоне через outbox.

## 6. Временные и постоянные ошибки
- **Временная** — пройдёт сама (база перезагружалась, сеть). Повтор поможет → 5xx / 503.
- **Постоянная** — повтор не поможет (сумма не та). Не заставлять повторять:
  принять (200), записать аномалию, алерт, ручной разбор.
- Аналитик выясняет у провайдера: на какие коды вы повторяете? Сколько раз? С какими паузами?
- Таймаут = неизвестность: операция могла пройти. Повторять только с тем же ключом идемпотентности.

## 7. Пагинация
Оба способа отдают данные порциями. Разница — как попасть на следующую.
| | Offset (номер страницы) | Cursor (закладка) |
|---|---|---|
| Запрос | `?page=5` | `?cursor=<из next_cursor>` |
| Прыжок на любую страницу | да | нет |
| Скорость на дальних страницах | падает | постоянная |
| Новые записи во время листания | дубли и пропуски | корректно |
| Для чего | таблица в админке | лента, опрос новых записей |
`next_cursor: null` — страниц больше нет.

## 8. Тестирование API
Проверяем 5 уровней: код → заголовки → структура → значения → бизнес-правила.
- Каждый код из контракта = минимум один тест.
- Классы эквивалентности: из группы одинаково ведущих себя значений берём одно.
- Граничные значения: ошибки на границах. limit 1..100 → проверяем 0, 1, 100, 101.
- Ловушка пустого списка: «у всех заказов статус X» проходит на пустом списке → сначала проверить, что не пусто.
- Тесты не зависят друг от друга и не портят данные для следующего запуска.
- Регрессия: тест ловит, когда правка сломала старое обещание контракта.
