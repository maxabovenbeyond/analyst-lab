# Индексы, EXPLAIN и транзакции

Эксперименты на таблице `perf.status_log` (2 млн строк, имитация истории статусов заказов)
и на схеме `delivery` сервиса доставки. PostgreSQL 17, Docker, домашний ПК.

## 1. Эксперименты с индексами

| Эксперимент | Плохой вариант | Хороший вариант | План выполнения |
|---|---|---|---|
| 1. Поиск истории по `order_id` | Без индекса: ‹ваше› мс (ориентир: 50–200 мс) | С индексом: ‹ваше› мс (ориентир: < 1 мс) | `Parallel Seq Scan` → `Bitmap Index Scan` / `Index Scan` |
| 2. Фильтр по дате | `changed_at::date = '2026-09-15'`: ‹ваше› мс | `changed_at >= '2026-09-15' AND changed_at < '2026-09-16'`: ‹ваше› мс | `Seq Scan` → `Index Only Scan` |
| 3. Порядок колонок в составном индексе | `(changed_at, status)`: Buffers ‹ваше› | `(status, changed_at)`: Buffers ‹ваше› (ориентир: в 3–7 раз меньше) | В обоих `Index Scan`, но разный объём чтения |
| 4. Низкая селективность | `status = 'DELIVERED'` (~1/7 таблицы, ~285 тыс. строк) | — | Планировщик выбрал `Seq Scan`, хотя индекс подходит |

## 2. Выводы

1. **Индекс по колонке поиска ускоряет точечные запросы в сотни раз.** Без индекса база читает
   все 2 млн строк и отбрасывает почти все (`Rows Removed by Filter`).
2. **Функция над колонкой отключает индекс.** Индекс хранит значения `changed_at`, а не
   `changed_at::date`. Условие нужно писать по самой колонке — диапазоном. То же касается
   `lower(...)`, `LIKE '%...'`, несовпадения типов.
3. **Порядок колонок в составном индексе: сначала «равно», потом диапазон.** Индекс
   `(status, changed_at)` сразу находит участок нужного статуса и внутри него — период.
   Индекс `(changed_at, status)` просматривает все события периода и отбрасывает лишние.
4. **Индекс полезен, когда условие отбирает малую долю строк.** Если подходит каждая
   седьмая строка, последовательное чтение дешевле, и планировщик сам выбирает `Seq Scan`.
5. **PostgreSQL не создаёт индексы для внешних ключей автоматически** — только для
   PRIMARY KEY и UNIQUE. В схеме `delivery` индексы по FK добавлены вручную (`ddl.sql`).
   Для `order_item.order_id` отдельный индекс не нужен: его покрывает уникальный индекс
   `(order_id, product_id)`, где `order_id` стоит первым (правило левого префикса).
6. **Индексы следуют из требований.** `orders (status, created_at)` — из sequence-диаграммы:
   кабинет магазина каждые 15 секунд запрашивает оплаченные заказы.
   `order_status_history (order_id, changed_at)` — из US-08: поддержка смотрит историю заказа.

## 3. Транзакции: двойной возврат по претензии

Сценарий: два оператора поддержки одновременно одобряют одну претензию (два подключения к БД).

| Подход | Что произошло | Итог |
|---|---|---|
| Наивный: прочитать статус → если OPEN, одобрить и вернуть деньги | Оба оператора увидели OPEN. Второй `UPDATE` выполнился, второй `INSERT` возврата упал с `duplicate key ... payment_provider_payment_id_key` | Двойной возврат предотвратило **только** ограничение `UNIQUE` на `provider_payment_id` |
| `SELECT ... FOR UPDATE` | Второе подключение ждало, пока первое не завершит транзакцию, и затем увидело статус APPROVED | Второй оператор не выполнил повторный возврат |
| Условное обновление `UPDATE ... WHERE status = 'OPEN' RETURNING id` | Первый запрос обновил строку, второй вернул 0 строк | Приложение понимает, что претензия уже обработана |

**Вывод:** защита строится в несколько слоёв. Блокировка или условное обновление — в логике
приложения, ограничение `UNIQUE` — страховка в базе на случай ошибки в коде. Это тот же принцип
идемпотентности, что и для повторных вебхуков платёжного провайдера (US-15).

## 4. Вопросы с собеседований

**Почему нельзя создать индекс на каждую колонку?**
Каждый индекс замедляет запись: при `INSERT`, `UPDATE` и `DELETE` база обновляет не только
таблицу, но и все её индексы. Индексы занимают место на диске и в памяти. Планировщику сложнее
выбирать план. Индексы создают под конкретные частые запросы, а не «на всякий случай».

**В каком порядке ставить колонки в составном индексе?**
Сначала колонки с условием равенства, потом колонку с диапазоном или сортировкой. Индекс работает
по правилу левого префикса: индекс `(a, b)` помогает запросам по `a` и по `a + b`, но не по
одной `b`.

**Как не допустить двойной обработки одной операции двумя пользователями?**
Три способа, которые сочетают между собой:
1. Блокировка строки при чтении: `SELECT ... FOR UPDATE` внутри транзакции.
2. Атомарное условное обновление: `UPDATE ... WHERE status = 'OPEN'` и проверка числа
   изменённых строк.
3. Ограничение уникальности в базе (идемпотентный ключ операции) как последний рубеж защиты.
