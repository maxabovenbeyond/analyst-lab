# Каталог событий сервиса заказов

Топик: `order-events`. Ключ: `order_id` (все события заказа — в одной партиции, строгий порядок).
Партиций: 3. Хранение: 7 дней. Гарантия доставки: at-least-once, потребители идемпотентны по `event_id`.

## Каталог

| Событие | Когда публикуется (переход) | Источник факта | Подписчики | Зачем подписчику |
|---|---|---|---|---|
| OrderPaid | AWAITING_PAYMENT → PAID | Вебхук платёжного провайдера | Уведомления, Фискализация, Аналитика | Сообщить магазину о новом заказе (US-10); отправить чек в ОФД; учесть выручку |
| OrderAccepted | PAID → ASSEMBLING | Команда магазина accept | Уведомления, Аналитика | Сообщить клиенту, что магазин начал сборку; время подтверждения магазином |
| OrderAssembled | ASSEMBLING → AWAITING_COURIER | Команда магазина assembled | Уведомления, Аналитика, служба доставки | Сообщить клиенту, что заказ ожидает курьера, время сбора заказа, Запуск процесса поиска курьера службой доставки (US-16) |
| OrderPickedUp | AWAITING_COURIER → IN_DELIVERY | Вебхук службы доставки | Уведомления, Аналитика | Сообщить клиенту, что курьер в пути; время ожидания курьера |
| OrderDelivered | IN_DELIVERY → DELIVERED | Вебхук службы доставки | Уведомления, Аналитика | Сообщить клиенту, что заказ доставлен, чтобы он начал процесс возврата (US-05), оставил отзыв (US-04); время доставки |
| OrderCancelled | любой → CANCELLED | Клиент, поддержка, магазин, таймер | Уведомления, Аналитика | Сообщить клиенту о запуске процесса возврата средств, если заказ был оплачен, уведомление службе доставке о прекращении исполнения заказа |

## Решения

1. Один топик на заказ, а не на тип события — чтобы сохранить порядок событий одного заказа.
2. События от внешних систем переводятся в наши (антикоррупционный слой): подписчики не зависят от провайдера.
3. Персональные данные клиента в события не кладём: передаём customer_id (152-ФЗ).


## Формат событий

Конверт (общий для всех): event_id, event_type, event_version, occurred_at, producer, correlation_id, payload.

### OrderPaid (v1)
| Поле payload | Тип | Обяз. | Описание |
|---|---|---|---|
| order_id | integer | да | Номер заказа |
| shop_id | integer | да | Магазин |
| customer_id | integer | да | Клиент (без персональных данных) |
| amount | number | да | Оплаченная сумма, ₽ |
| paid_at | date-time | да | Момент оплаты у провайдера |

### OrderCancelled (v1)
| Поле payload | Тип | Обяз. | Описание |
|---|---|---|---|
| order_id | integer | да | Номер заказа |
| shop_id | integer | да | Магазин |
| customer_id | integer | да | Клиент (без персональных данных) |
| previous_status | string (OrderStatus) | да | Из какого статуса отменён. Доставка: AWAITING_COURIER → отменить заявку у провайдера |
| cancelled_by | string: CUSTOMER / SHOP / SUPPORT / SYSTEM | да | Кто инициировал. Уведомления: выбор текста |
| reason | string | да | Причина (как cancel_reason в БД). Аналитика: отмены по причинам |
| paid_amount | number | да | Сколько было оплачено, ₽. 0 — не оплачен. Платежи: > 0 → инициировать возврат |
| cancelled_at | date-time | да | Момент отмены |

## Изменения формата

| Изменение в OrderPaid | Совместимое? | Что делать |
|---|---|---|
| Добавить необязательное поле `promised_at` | Да | Добавить в v1. Читатели, которым оно не нужно, проигнорируют (tolerant reader) |
| Переименовать `amount` в `total_amount` | Нет | Расширить и сузить: сначала публиковать ОБА поля в v1 (добавление совместимо), пометить `amount` устаревшим, перевести читателей, затем удалить `amount` в v2 |
| Поменять тип `order_id` на строку | Нет | Новая версия v2. Какое-то время публиковать v1 и v2 параллельно, читатели переходят по очереди, затем v1 отключается |
| Удалить поле `customer_id` | Нет | Сначала выяснить, кто из подписчиков его использует (каталог событий!). Пометить устаревшим, договориться о сроке, удалить в v2 |
