# Шпаргалка: асинхронные интеграции

## 1. Синхронно vs асинхронно
| | Синхронно (REST) | Асинхронно (события) |
|---|---|---|
| Аналогия | Телефонный звонок | Письмо в общий чат |
| Отправитель ждёт ответа | Да | Нет |
| Получатель доступен сейчас | Обязательно | Не обязательно |
| Получателей | Один | Сколько угодно |
Событие вместо 5 вызовов решает: скорость, устойчивость (сбой SMS не блокирует оплату),
слабую связанность (новый подписчик — без правок отправителя).
Команда — «сделай» (один получатель, может отказать). Событие — «случилось» (факт, получателей много).

## 2. Kafka vs RabbitMQ
| | Kafka (журнал) | RabbitMQ (очередь) |
|---|---|---|
| После чтения | Остаётся | Удаляется |
| Многим получателям | Естественно | Нужна настройка |
| Перечитать | Да | Нет |
| Для чего | Поток событий между сервисами | Распределение задач между исполнителями |

## 3. Устройство Kafka
- **Топик** — тематический журнал (`order-events`).
- **Партиция** — параллельная дорожка (касса). **Порядок — только внутри партиции.**
- **Ключ сообщения** — определяет партицию: `хеш(ключ) % число_партиций`.
  Одинаковый ключ → одна партиция → строгий порядок. Ключ НЕ уникален.
- **Группа** — отдел. Разные группы получают ВСЁ; внутри группы участники ДЕЛЯТ партиции.
- **Offset** — закладка группы. Можно сдвинуть назад и перечитать.
- Имя группы = идентичность потребителя (новый сервис со старым именем унаследует закладку).

⭐ **Ключ сообщения ≠ event_id**
| | Ключ сообщения | event_id |
|---|---|---|
| Уникален | Нет (у всех событий заказа одинаков) | Да |
| Зачем | Партиция → ПОРЯДОК | Распознать повтор → ИДЕМПОТЕНТНОСТЬ |
| Пример | `8001` | `7f3c9a2e-...` |

## 4. Формат события
Конверт: event_id, event_type, event_version, occurred_at, producer, correlation_id + payload.
- event_id — уникальный номер события (защита от дублей).
- correlation_id — номер всей цепочки (поиск по логам всех сервисов).
- **Тонкое** — только id, подписчик идёт в API за деталями. **Толстое** — всё нужное внутри.
  Правило: то, что нужно типичным подписчикам; без персональных данных (152-ФЗ).
- Одно событие = один факт. Отмена и возврат — разные события.
- Один топик на сущность (не на тип события) — чтобы сохранить порядок.
- Внешние события переводим в свои (антикоррупционный слой).

## 5. Версионирование
- Безопасно: добавить необязательное поле.
- Опасно: удалить, переименовать, сменить тип, добавить значение в enum.
- Несовместимое: v2, публиковать v1 и v2 параллельно, перевести подписчиков, отключить v1.
- Переименование — «расширить и сузить»: публиковать оба поля → перевести → удалить старое.
- Терпимый читатель: подписчики игнорируют незнакомые поля.

## 6. Transactional Outbox
Проблема — двойная запись: база и Kafka без общей транзакции.
- база → Kafka: событие может потеряться; Kafka → база: событие о неслучившемся.
Решение: событие пишется в таблицу outbox **в той же транзакции**, что и изменение данных.
Курьер (relay) забирает неотправленные, публикует в Kafka, отмечает published_at.
Подписчики читают Kafka, а не outbox.
- Порядок курьера: сначала опубликовать, потом отметить → худшее — дубль, не потеря.
- Гарантия at-least-once → потребители обязаны быть идемпотентны по event_id.
- Мониторинг: возраст самого старого неотправленного (> 1–2 мин — тревога), количество.

## 7. Потребитель
- Журнал входящих (inbox) по event_id; журнал и действие — одна транзакция.
- **Закладку фиксировать ПОСЛЕ обработки**: при сбое будет дубль (безопасно), а не потеря.
- Постоянная ошибка (битый формат) → сразу DLQ. Временная (шлюз) → повторы с паузой → DLQ.
- DLQ: сохранять причину и источник (топик, партиция, offset). Алерт, владелец, срок разбора.
- Опасность повторной отправки из DLQ — нарушение порядка (курьер к отменённому заказу).
  Для потребителей, которым важен порядок, при сбое откладывать ВСЕ события того же ключа.

## 8. Сага
Распределённый процесс без общей транзакции: шаги + компенсация для каждого шага.
- **Откат** — техническая отмена внутри одной транзакции до фиксации, следов нет.
- **Компенсация** — новое бизнес-действие после фиксации, следы остаются (возврат, новое SMS).
- Компенсации: в обратном порядке; идемпотентные; обязаны завершиться (иначе — ручной процесс).
- Сначала остановить то, что ещё может произойти (отменить курьера), потом вернуть деньги.
- **Поворотная точка** — после неё отмена невозможна (у нас — курьер забрал), только исключения.
- **Хореография** — сервисы реагируют на события сами. Просто, но процесс «размазан».
- **Оркестрация** — дирижёр командует шагами, хранит состояние, ведёт таймеры.
- Выбор: число шагов, таймеры, компенсации, нужна ли прозрачность. Много → оркестрация (BPMN, Camunda).
